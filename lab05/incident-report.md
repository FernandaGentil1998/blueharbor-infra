# Lab 05.5 — Incident Report

## 1. Executive Summary

During the incident-response exercise, Suricata, UFW, SSH authentication logging, and Fail2ban were inspected and tested on WEB01.

The collected evidence confirms:
- Suricata generated four ICMP test alerts on 2026-11-23 from WEB02 to WEB01.
- UFW blocked five incoming TCP packets from external address `91.189.91.83`.
- SSH recorded one invalid-user attempt originating locally from WEB01 and five invalid-user attempts from WEB02.
- Fail2ban reported six total failures and one banned address, `10.10.20.21`.
- A network scan from WEB02 found TCP port 139 on DC01 filtered.

No successful unauthorized SSH login or confirmed system compromise was identified.

The timeline below combines timestamped observations from different sources. These events are not assumed to be part of one attack because their sources, times, and traffic characteristics differ.

## 3. Evidence Collected

### 3.1 Suricata — ICMP Alerts

**Evidence file:** `evidence/suricata-icmp-2026-11-23-local.log`

Four ICMP test alerts were recorded on 2026-11-23:
- Source: WEB02 (`10.10.20.21`)
- Destination: WEB01 (`10.10.20.20`)
- Local timestamps: 16:04:04–16:04:07 CET
- UTC timestamps: 15:04:04–15:04:07 UTC

The alerts were generated by the local test rule `BLUEHARBOR ICMP TEST`.

Eight earlier ICMP test alert lines from 2026-11-17 were also observed in the Suricata log. They represent earlier validation activity and are not included in the 2026-11-23 incident timeline.

### 3.2 Fail2ban — SSH Protection

**Command:** `sudo fail2ban-client status sshd`

An initial inspection reported zero failures and zero banned addresses. This was a baseline observation made before the controlled SSH test.

After the controlled test, the final Fail2ban status reported:

- Currently failed: 1
- Total failed: 6
- Currently banned: 1
- Total banned: 1
- Banned IP list: `10.10.20.21`

The SSH jail configuration was inspected:

| Setting | Value |
|---|---:|
| Jail | sshd |
| maxretry | 5 |
| findtime | 600 seconds |
| bantime | 600 seconds |

The evidence confirms that Fail2ban detected repeated SSH failures and banned the WEB02 source IP. The configured ban duration is 600 seconds; expiration was not independently verified.

### 3.3 SSH Authentication Logs

**Evidence file:** `evidence/ssh-authentication-utc.log`

The WEB01 SSH journal recorded six invalid-user events:
- One event originated locally from WEB01 (`10.10.20.20`) at 15:13:42 UTC.
- Five events originated from WEB02 (`10.10.20.21`) between 15:15:29 and 15:16:27 UTC.

The controlled WEB02 test used the invalid account `testuser`. SSH returned:

`Permission denied (publickey)`

A corresponding connection-closed event was recorded for each invalid-user attempt. These paired connection-closed records are not counted as separate authentication attempts.

SSH password authentication was disabled and public-key authentication was enabled during the test. No successful login was observed.

The six invalid-user events are consistent with the final Fail2ban total of six failures. The source addresses show that one event came from the local host and five came from WEB02.

### 3.4 UFW — Firewall Blocking Activity

**Evidence file:** `evidence/ufw-blocks-2026-11-23.log`

Five UFW BLOCK records were preserved on 2026-11-23.

Observed details:
- Source: `91.189.91.83`
- Destination: WEB01 (`10.10.20.20`)
- Protocol: TCP
- Source port: 80
- Destination port: 54846
- Local timestamps: 11:28:12–11:28:22 CET
- UTC timestamps: 10:28:12–10:28:22 UTC

These packets were blocked by UFW on interface `enp0s3`. Their source and timing differ from the later controlled WEB02 SSH test. The available evidence does not establish the identity or intent of the external source.

### 3.5 Network Scan — DC01

**Evidence file:** `evidence/dc01-port139-nmap.txt`

A service-detection scan was executed from WEB02 against DC01 (`10.10.10.10`):

`sudo nmap -sV -p 139 10.10.10.10`

Result:

`139/tcp filtered netbios-ssn`

The result indicates that TCP port 139 did not respond to the scan and was filtered by a network control or firewall. The scan output was preserved.

### 3.6 Network Connectivity Between WEB02 and WEB01

The controlled test environment was verified before the SSH simulation:

- WEB02 address: `10.10.20.21/24`
- WEB01 address: `10.10.20.20`
- ICMP connectivity: 4 packets transmitted, 4 received, 0% packet loss.
- TCP port 22: reachable from WEB02.

This confirms that WEB02 was available as a test source during the later validation.

## 5. Impact Assessment

No confirmed system compromise or successful unauthorized SSH access was identified from the collected evidence.

The controlled SSH test demonstrated repeated invalid-user authentication attempts from WEB02 and a subsequent Fail2ban ban of its IP address.

UFW blocked incoming TCP packets from an external address. Suricata generated alerts for the controlled ICMP test traffic. The DC01 scan reported port 139 as filtered.

The available records do not establish the intent or impact of the external traffic.

## 6. Detection

The following security controls provided observable evidence:

- **Suricata:** generated ICMP alerts for controlled test traffic.
- **UFW:** recorded and blocked incoming TCP packets.
- **Fail2ban:** detected repeated SSH authentication failures and banned `10.10.20.21`.
- **SSH journal:** recorded invalid-user attempts and connection events.
- **Nmap:** confirmed that TCP port 139 on DC01 was filtered from the WEB02 test source.

## 7. Containment

UFW blocked the incoming packets recorded in its logs.

Fail2ban provided an additional containment action by banning the WEB02 source IP `10.10.20.21` after repeated SSH authentication failures.

The configured ban duration was 600 seconds. The ban expiration was not independently verified.

## 8. Eradication and Recovery

No confirmed compromise was identified. Therefore, no eradication or recovery operation was justified based on the available evidence.

The temporary Fail2ban ban was a defensive response to the controlled test, not evidence of a compromised host.

## 9. Lessons Learned

- Centralized and timestamped logs are essential for incident reconstruction.
- Local timestamps must be converted consistently before building a UTC timeline.
- Suricata alerts should be compared with firewall and authentication logs without assuming causation.
- Fail2ban status should be checked alongside SSH authentication records.
- Evidence should be exported and preserved immediately after each test.
- Controlled tests should record the source IP, destination, command, timestamp, and resulting security-control response.
- A working test source and target are necessary for repeatable network simulations.
