\# Lab 05.5 — Incident Report



\## 1. Executive Summary



During the incident drill, security monitoring controls on WEB01 were inspected to identify suspicious network activity and verify the effectiveness of host-level security mechanisms.



Suricata generated ICMP alerts, UFW recorded blocked incoming traffic, and Fail2ban was confirmed active. No SSH authentication failures or successful SSH logins were found in the inspected 30-minute journal window.



The full attack simulation from WEB02 could not be completed. Therefore, the available evidence does not establish a complete attack sequence or confirm a security compromise.

\## 3. Evidence Collected



\### 3.1 Suricata — ICMP Alerts



\*\*Evidence file:\*\* `/var/log/suricata/fast.log`



Eight ICMP test alert lines were observed in the Suricata fast log.



This confirms that Suricata generated alerts for ICMP traffic. The complete alert details, including source addresses and individual timestamps, were not retained in the collected notes.



\### 3.2 Fail2ban — SSH Protection



\*\*Command:\*\* `sudo fail2ban-client status sshd`



Observed results:



\- Currently failed: 0

\- Total failed: 0

\- Currently banned: 0

\- Total banned: 0



Fail2ban was active, but no SSH failures or banned IP addresses were recorded at the time of inspection.



\### 3.3 SSH Authentication Logs



\*\*Command:\*\* `sudo journalctl -u ssh --since "-30 min" --no-pager`



The inspected output contained SSH service startup messages (`systemd started ssh.service`).



No matching failed authentication, invalid user, accepted login, or authentication event was found in the filtered 30-minute window.



\### 3.4 UFW — Firewall Blocking Activity



\*\*Evidence file:\*\* `/var/log/syslog`



Multiple kernel log entries containing `UFW BLOCK` were observed.



The records indicate that UFW blocked incoming traffic on interface `enp0s3`.



The complete source and destination details were not retained in the collected notes.

\*\*Timeline limitation:\*\* The available notes do not contain exact timestamps for each event. The WEB01 system clock was reported as `2026-11-16 09:29:57 UTC` during evidence collection. This is a collection timestamp, not the confirmed time of the ICMP or UFW events.



The exercise checkpoint requested at least six timestamped events. The available evidence is insufficient to establish six distinct, timestamped events.



\## 5. Impact Assessment



No confirmed system compromise or unauthorized SSH access was identified from the collected evidence.



UFW blocking activity and Suricata ICMP alerts demonstrate security monitoring and blocking activity. However, the available records are insufficient to determine the full origin, intent, or impact of the observed network traffic.



\## 6. Detection



The following security controls provided observable evidence:



\- \*\*Suricata:\*\* generated ICMP alerts.

\- \*\*UFW:\*\* recorded blocked incoming traffic.

\- \*\*Fail2ban:\*\* SSH protection service was active.

\- \*\*SSH journal:\*\* available for authentication and service event investigation.



\## 7. Containment



UFW blocked incoming traffic according to the system logs.



No additional manual containment action or IP-specific blocking action was documented during this exercise.



\## 8. Eradication and Recovery



No confirmed compromise was identified. Therefore, no eradication or recovery operation was justified based on the available evidence.



\## 9. Lessons Learned



\- Centralized and timestamped logs are essential for incident reconstruction.

\- Suricata alerts should be correlated with firewall and authentication logs.

\- Fail2ban status should be checked alongside SSH authentication records.

\- Evidence should be exported and preserved immediately after each test.

\- Network attack simulations require a functioning test source and target.
