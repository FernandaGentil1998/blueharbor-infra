# BlueHarbor — Secrets Inventory and Management

## 1. Purpose

This document inventories the credentials and sensitive configuration used by the BlueHarbor project.

It records their purpose, storage location, access scope, rotation considerations and incident-handling requirements.

No actual secret values, passwords, API tokens or private keys are stored in this document.

## 2. Secrets and Credential Inventory

| Credential | Purpose | Storage / delivery | Access scope | Status |
|---|---|---|---|---|
| `SUPABASE_URL` | Supabase project endpoint | Application environment variable | TrackIt application | Configured through environment |
| `SUPABASE_KEY` | Supabase API authentication | Application environment variable | TrackIt application | Publishable key; not a service-role key |
| `GITHUB_TOKEN` | GitHub Actions authentication | Automatically generated by GitHub Actions | Workflow permissions | Used by CI |
| Vercel API token | Terraform provider authentication | Provider authentication mechanism; exact configured source not verified | Terraform execution identity | Requires verification |
| Terraform state | Infrastructure state and resource metadata | Local `cloud/platform/terraform.tfstate` | Local filesystem access | Ignored by Git; potentially sensitive |

`SUPABASE_URL` is an endpoint identifier rather than a secret by itself. The publishable Supabase key is intended for client/application use and does not replace server-side authorization or Row Level Security.

The application reads `SUPABASE_URL` and `SUPABASE_KEY` from environment variables. Their literal values are not defined in `trackit/app.py`.

## 3. Storage and Access Controls

### Application credentials

- The TrackIt application obtains Supabase configuration from environment variables.
- Credential values must not be committed to source code, configuration files or logs.
- The Supabase publishable key must be protected by appropriate database permissions and Row Level Security policies.
- A Supabase service-role key must never be exposed to the browser or an untrusted application client.

### GitHub Actions

- `GITHUB_TOKEN` is generated by GitHub Actions for workflow authentication.
- The CI workflow declares `contents: read` and `packages: write` permissions at workflow level.
- Workflow permissions should be restricted to the minimum required by each job.
- Long-lived personal access tokens should not be used when the built-in token is sufficient.

### Terraform

- `cloud/platform/terraform.tfstate` is ignored by Git through `cloud/platform/.gitignore`.
- Ignoring the state file prevents it from being tracked by Git, but does not encrypt it or restrict local filesystem access.
- Terraform state must be treated as potentially sensitive.
- A remote state backend with encryption, access control and locking should be considered before production use.
- The Vercel provider credential source and its access permissions still require verification.

## 4. Rotation and Revocation

A complete automated credential rotation process has not been demonstrated in the repository.

The following lifecycle should be applied:

1. Identify the affected credential and all systems that consume it.
2. Create or provision a replacement credential with the minimum required permissions.
3. Update the relevant environment or secret store.
4. Validate application and infrastructure access with the replacement.
5. Revoke the old credential.
6. Record the rotation date, responsible owner and validation evidence.

Credentials should also be rotated immediately after suspected exposure, unauthorized access or personnel access changes that require revocation.

No completed Vercel token rotation is claimed by this document.

## 5. Incident Handling

If a credential is exposed:

1. Revoke or disable the affected credential as soon as possible.
2. Generate a replacement using least privilege.
3. Update all dependent applications, workflows and infrastructure configurations.
4. Review Git history, CI logs, application logs and provider audit events for exposure or misuse.
5. Remove the exposed value from active files and history where appropriate.
6. Validate that the replacement works and the old credential no longer grants access.
7. Document the incident, impact, timeline and remediation evidence.

Deleting a secret from the latest commit does not remove it from previous Git history. Repository history must be assessed separately.

## 6. Known Gaps

The following controls remain unverified or incomplete:

- Centralized secrets management and encryption key lifecycle management.
- Verified storage location and access policy for the Vercel API token.
- Formal credential ownership and periodic access reviews.
- Documented and tested credential rotation procedures.
- Gitleaks scanning of the complete Git history.
- Verification that Terraform state contains no exposed credentials.
- GitHub secret scanning and push protection configuration.
- Evidence of MFA enforcement for GitHub, Vercel and Supabase.
- Job-level least-privilege permissions for GitHub Actions.

These items must not be considered implemented until supporting evidence is collected.

## Terraform State Security Review

The local Terraform state at `cloud/platform/terraform.tfstate` is excluded from Git through the `*.tfstate` rule in `cloud/platform/.gitignore`.

A metadata-only inspection identified:
- Terraform version: 1.17.1
- Resources: 2 (`vercel_project` and `vercel_project_environment_variable`)
- Outputs: 1 (`project_id`), not marked sensitive
- The `vercel_project_environment_variable` resource contains attributes marked as sensitive.

Sensitive attribute values were not displayed or copied during the review.

**Risk:** Git exclusion prevents accidental repository commits but does not provide encryption at rest, access control, or secure state sharing.

**Required improvements before production:**
- Use a remote Terraform backend with encryption at rest.
- Restrict state access to authorized identities.
- Enable state locking and access auditing where supported.
- Keep state files and backups out of Git and public artifacts.
- Review state contents securely before sharing or migrating them.
